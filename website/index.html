01 · What it is

Overview

One line

Zedd Weather is an edge telemetry and risk-analysis platform that reads real micro-climate data from Raspberry Pi hardware, runs AI analysis on the device, and turns raw readings into actionable safety, crop, and operations guidance — all while cryptographically attesting each decision to the Minima blockchain.

The stack, at a glance

  • Hardware-first — real Sense HAT, AI HAT+ (Hailo-8L NPU), Enviro+, Modbus sensors
  • On-device AI — NPU → Ollama/Gemma → Gemini fallback chain
  • React 19 dashboard with live telemetry, charts & AI reports
  • FastAPI backend with sector risk engines & alert rules
  • InfluxDB + Grafana time-series storage and dashboards
  • MQTT publish/subscribe between cluster nodes
  • Docker Compose local stack and 3-node cluster simulation
PiNet OS DApp. The dashboard also runs as a sandboxed DApp inside the PiNet OS desktop. A typed bridge SDK (src/pinet-sdk.ts) talks to the PiNet host over postMessage for wallet, balance and block events, so the app can participate in the Minima network from within a browser iframe.

02 · Physical kit

Hardware

The production Raspberry Pi Weather Node is a sensor-rich board: a Sense HAT v2 for environment readings, an AI HAT+ carrying a Hailo-8L NPU for inference, and an M.2 NVMe SSD for buffering and model storage — extended with GPIO, I2C and Modbus peripherals.

Sense HAT v2

Environmental + IMU sensors: temperature (with CPU-heat compensation), humidity, pressure, plus orientation — and an 8×8 RGB LED matrix that renders the live risk colour on the device.

AI HAT+ · Hailo-8L NPU

A M.2 Key E 26 TOPS accelerator that runs a compiled weather_classify.hef model on-device — weather classification and anomaly scoring with no cloud connection.

M.2 NVMe SSD

Fast local telemetry buffer and model artifact storage. Keeps the SD card out of the write path and survives broker outages.

VEML6075 UV sensor

I2C UV-A/B radiometer feeding the UV index used by worker-safety and exposure-limit logic across all three sector engines.

Pimoroni Enviro+

Air quality, gas and particulate-matter sensing — provides the AQI metric used for respiratory-protection rules.

GPIO + Modbus RS485

Tipping-bucket rain gauge (0.2794 mm/tip), buzzer/LED alarm outputs, and Waveshare RS485 CAN HAT for industrial anemometer & rain-gauge units.

Graceful degradation. Every driver is optional and feature-flagged (SENSE_HAT_ENABLED, ENVIRO_PLUS_ENABLED, MODBUS_ENABLED, …). When hardware is absent, a deterministic simulator oscillates readings so the whole platform still runs end-to-end on any host.

03 · How it fits together

Architecture

Data flows from real sensors → MQTT → AI worker → storage → dashboard & ledger. The three-node cluster splits the workloads the same way a physical Raspberry Pi weather network does.

Node C Sensory worker Sense HAT · Enviro+ · UV · Modbus · MQTT publisher
→
Node B AI worker Hailo-8L NPU → Ollama/Gemma → Gemini · attestation
→
Node A Control plane + storage InfluxDB · Grafana · Open WebUI · FastAPI · React

A Control plane + storage

Hosts InfluxDB 2.7 (time-series telemetry), Grafana dashboards, Open WebUI (LLM front-end) and the FastAPI backend that powers the React dashboard.

  • InfluxDB on :8086 (org zedd-weather, bucket telemetry)
  • Grafana on :3000
  • Open WebUI on :8080
  • Vite dev server on :5173

B AI worker

Subscribes to MQTT telemetry, ingests Meteomatics macro forecasts, and runs inference through the Hailo-8L NPU with fallback to local Ollama / Gemma and the Gemini API.

  • Cross-references micro & macro weather
  • Generates mitigation directives (e.g. HALT_HEAVY_MACHINERY_HEAT_RISK)
  • SHA-256 attests each directive to the Minima ledger

C Sensory worker

Aggregates every enabled sensor into one telemetry payload and publishes it to MQTT with automatic broker failover and QoS 1.

  • Drives the Sense HAT LED matrix with the live risk colour
  • Evaluates GPIO buzzer/LED alarms from configurable thresholds
  • Buffers locally on NVMe/SQLite during outages

Offline resilience

The edge collector writes to InfluxDB and, when unreachable, falls back to a SQLite buffer (/tmp/zedd_buffer.db) that auto-flushes when connectivity returns. A liveness file (/tmp/zedd-alive) is touched each cycle so container health checks detect hangs.

Anomaly detection

Two-stage validation on every reading:

  1. Physical bounds — impossible values (e.g. −50…85 °C, 870…1085 hPa) are flagged
  2. Z-score — a rolling 20-point window flags readings > 4σ from the mean

Anomalies are persisted, surfaced as alerts, and excluded from safe-to-proceed logic.

Server-side keys

Google Weather API and Gemini calls are proxied by the FastAPI backend, so API keys never reach the browser. The browser only ever talks to /api/… and public Open-Meteo endpoints.

05 · Domain engines

Sector intelligence

One telemetry snapshot, three lenses. Each engine is a deterministic, rule-based heuristic — no ML libraries required — so it runs anywhere and is fully auditable.

What it outputs

  • Worker safety — WBGT-inspired heat index, wind-chill, work↔rest ratio, hydration (L/hr), PPE list
  • Work window — safe-to-proceed flag with halt/caution reasons, delay & next-check hours
  • Weather hazards — wind, lightning/storm, heat, cold, rain with mitigations
  • Material risks — concrete curing, steel condensation/ice, paint adhesion, timber moisture

Key thresholds

  • Wind: caution 10 m/s · halt 18 m/s
  • Heat: caution 30 °C · extreme 40 °C
  • Cold: caution 5 °C · extreme −10 °C
  • Storm risk below 995 hPa (+ humidity > 75%)
  • Rothfusz heat-index & North-American wind-chill formulas
Example directive: HALT: Wind speed 19.2 m/s exceeds halt limit (18.0 m/s). — with an immediate “secure crane and elevated work” mitigation.

What it outputs

  • Soil moisture — estimated VWC % (Hargreaves-style ET proxy), confidence, days-to-irrigation
  • Irrigation schedule — recommended / urgency / volume (mm) / next check
  • Pest risk — spider mites, aphids/whiteflies, locusts, stem borers
  • Disease risk — late blight, powdery mildew, Botrytis, leaf scorch
  • Weather stress — heat, cold, frost, humidity, pressure alerts

Crop profiles

Per-crop optima (temp, humidity, water requirement, frost-kill temperature) for maize and other crops drive irrigation and stress decisions.

  • High humidity >80% → fungal risk; <35% → mite risk
  • Frost-kill detection escalates to critical
  • Rainfall > 1.5× daily need cancels irrigation
Example directive: FROST RISK: Protect crops with frost cloth or smudge pots immediately.

What it outputs

  • Equipment safety — thermal-stress and corrosion-risk indices, ventilation flag
  • Operational window — safe-to-operate with halt/caution reasons
  • Process risks — equipment overheating/cold start, static discharge, vapour accumulation, AQI exposure
  • PPE — respiratory protection (P2/N95) when AQI rises; chemical PPE for chemical/refinery sites

Facility-specific logic

  • Wind: caution 12 m/s · halt 22 m/s
  • chemical/refinery: static-discharge & vapour-dispersion rules
  • AQI halt/caution thresholds from facility profile
  • Logistics disruption when rainfall > 10 mm
Example directive: Static Discharge: Low humidity (22%) increases electrostatic discharge risk — activate humidification and enforce grounding.

07 · On-chain attestation

RMPE-2 sovereign weather protocol

Every weather observation, policy evaluation and mitigation directive can be committed to the Minima blockchain as a weather coin. The sovereign engine composes and validates deterministic state transitions entirely from PREVSTATE plus cryptographic proofs.

Weather coin state

  • Protocol tag — RMPE2-WEATHER
  • Oracle root — committed Merkle root of the weather dataset
  • Phases — data_entry → consensus → distribution → settlement
  • Recursive layers — station identity, geo-fencing, policy, settlement
  • Budget — max depth 8, max proof 2048 bytes (256 bytes/depth)

What validation guarantees

  • Station identity and oracle root are stable across transitions
  • Weather timestamp and usage counter strictly increase (no oracle overuse)
  • Sequence advances one step; phases are linear and unskippable
  • Each recursive branch is preceded by an ASSERT PROOF membership proof
  • Proofs fit a bounded byte budget; RMP root must recompute from leaf + path

Network peer exchange — RNPE-2

Nodes reconcile consensus with peers through Recursive Network Peer Exchange: missing block ranges must be height-contiguous and hash-linked, must start from the local tip, and must terminate at the advertised consensus tip whose state root matches the recursive Merkle proof. Compatibility tooling exposes this via /api/sovereign/protocol, /api/sovereign/compose and /api/sovereign/validate.

Attestation flow

  1. Sensors publish telemetry over MQTT (Node C)
  2. AI worker runs inference and generates a mitigation directive (Node B)
  3. Directive is SHA-256 hashed into an attestation record (Minima-Zedd-v1)
  4. The dashboard splits directives into shards, stores/export them, and displays verified ledger attestations

08 · Inference

The AI fallback chain

Inference is designed to keep working offline. Each tier is tried in order, and the whole stack degrades gracefully to rule-based heuristics.

1 Hailo-8L NPU

Loads the HEF model at startup and keeps it resident on the NPU for low-latency weather classification (clear, cloudy, rain, storm, fog, snow).

2 Ollama / Gemma

Local gemma2:2b over OLLAMA_BASE_URL produces structured JSON risk reports — no cloud required.

3 Gemini API

Cloud fallback for richer telemetry/media/forecast/map analysis, grounded with Google Maps retrieval.

4 Heuristic fallback

Deterministic rules (temp/humidity/pressure thresholds) classify weather when every AI tier is unavailable.

11 · Run it

Deployment & quick start

Local stack

cp .env.example .env
# set INFLUXDB_TOKEN (and GEMINI_API_KEY optionally)

# Control plane + storage (Node A workloads)
docker compose up -d

# Add AI + sensory workers + MQTT (Nodes B & C simulation)
docker compose -f docker-compose.yml \
  -f docker-compose.cluster.yml up -d --build
  • InfluxDB → localhost:8086 · Grafana → localhost:3000
  • Open WebUI → localhost:8080 · MQTT → 1883

Frontend dev

npm install
npm run dev   # Vite on http://localhost:5173

# checks
npm run lint  # tsc --noEmit
npm run build # vite build → dist/

Production build output lands in dist/ and can be served by any static host.

Three-node cluster test

Single-host simulation

docker compose -f docker-compose.yml \
  -f docker-compose.cluster.yml up -d

docker exec zedd-mqtt mosquitto_sub \
  -t 'weather_station/#' -v
docker logs -f zedd-sensory-worker

Real multi-host (3 Pis)

  • Node A (control + storage): docker compose up -d
  • Node B (AI): MQTT_BROKER_HOST=<node-a-ip> docker compose -f docker-compose.cluster.yml up -d ai-worker mqtt-broker
  • Node C (sensory): MQTT_BROKER_HOST=<node-a-ip> docker compose -f docker-compose.cluster.yml up -d sensory-worker mqtt-broker
